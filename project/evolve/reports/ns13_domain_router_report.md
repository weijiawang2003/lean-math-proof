# NS13 — Domain-aware model routing

## Motivation

NS12 surfaced a clear Pareto tradeoff between the two fine-tuned
checkpoints we have on disk:

- `gen_v5_ns11_combined`: 9/38 medium, 13/65 large, **8/15 demo_v1**
- `gen_v5_ns12_balanced`: 5/38 medium, 6/65 large, **10/15 demo_v1**

Neither single model is dominant. NS11 wins on Nat, NS12 wins on
Set/Finset. Forcing both into one fine-tune trades off one for the
other (see
[ns12_anti_forgetting_report.md](./ns12_anti_forgetting_report.md)).

NS13 sidesteps the tradeoff: keep both checkpoints, and dispatch
at inference time by theorem domain.

## Implementation

A new policy type ``routed_generative`` (see
[routed_policy.py](../../../routed_policy.py)) holds a list of
``(regex_pattern, ckpt_dir)`` routes and lazily loads each
underlying ``GenerativePolicy`` on first hit. The route config is
a small JSON:

```json
{
  "routes": [
    {"pattern": "^Nat\\.",    "ckpt_dir": "project/models/gen_v5_ns11_combined"},
    {"pattern": "^Set\\.",    "ckpt_dir": "project/models/gen_v5_ns12_balanced"},
    {"pattern": "^Finset\\.", "ckpt_dir": "project/models/gen_v5_ns12_balanced"}
  ],
  "default_ckpt_dir": "project/models/gen_v5_ns12_balanced"
}
```

(See [project/evolve/routing/ns13_router.json](../routing/ns13_router.json).)

Wired into `eval_rollout_all.py` via two new bits of plumbing:

- `--policy-type routed_generative` plus `--route-config <path>`
  selects the new policy directly.
- `--policy-type hybrid_evolved --route-config <path>` swaps the
  wrapper's inner base model for the router, so the NS9
  StrategyWrapperPolicy can also use it without code changes.

The router is *stateless* and *not learned*. Routes are matched in
order; first match wins; the default fires when no route matches.
No retraining. No new artifacts beyond a tiny config file.

## Evaluation matrix (raw, top-k=8 beam, max_steps=8)

| policy | medium (38) | large (65) | demo_v1 (15) | wrap.med | wrap.large |
|---|---:|---:|---:|---:|---:|
| raw gen_v5 (baseline) | 3 | — | 10 | 37 | 49 |
| raw `gen_v5_ns11_combined` | **9** | **13** | 8 | 37 | 49 |
| raw `gen_v5_ns12_balanced` | 5 | 6 | **10** | 37 | 49 |
| **raw `routed`** | **9** | **13** | **10** | **37** | **49** |
| **oracle union** (offline upper bound) | **9** | **13** | **10** | — | — |

Routing meets every primary success criterion:

- ✅ medium ≥ 9/38 — matches NS11.
- ✅ large ≥ 13/65 — matches NS11.
- ✅ demo_v1 = 10/15 — matches gen_v5 and NS12 balanced.
- ✅ wrapper preserved at 37/38 + 49/65 with `--policy-type
  hybrid_evolved --route-config …`.

## Per-theorem union analysis

Generated by [`scripts/ns13_compare_model_union.py`](../../../scripts/ns13_compare_model_union.py)
and saved to [ns13_model_union_analysis.md](./ns13_model_union_analysis.md).

Key findings:

1. **No exclusive single-model wins on any tested set.** Every
   theorem solved by some model is solved by at least one other
   model. The difference between ns11/ns12 is purely top-k
   re-ordering on the *same* underlying theorem coverage.
2. **The oracle union equals the best single model per set.** On
   medium, ns11_combined alone proves 9/38 and no other model adds
   anything. On demo_v1, gen_v5 / ns12_balanced both prove the
   same 10/15.
3. **The router achieves the oracle union exactly** on each set.
   Domain routing is *sufficient* — no per-theorem routing or
   ensembling is needed (within these models, on these sets).

Intersection (all five raw models prove this) on medium is 3
theorems; on large is 6; on demo_v1 is 8.

## Wrapper compatibility (Stage 5)

The NS9 strategy wrapper runs unchanged with the router as its
base:

```
python eval_rollout_all.py \
  --theorem-set nat_defs_medium \
  --policy-type hybrid_evolved \
  --strategy-config project/evolve/best/ns9_best_genome.json \
  --route-config project/evolve/routing/ns13_router.json \
  --ckpt-dir routed_placeholder \
  --top-k 8 --max-steps 8 --decode-mode beam
```

Result: medium 37/38, large 49/65 — identical to wrapper +
single-checkpoint runs. No regression. The wrapper already
overwhelms base-model differences on these sets (37/38 is the
ceiling sans `Nat.AM_GM`), so routing has no headroom here. But
crucially, **no regression** — meaning the router is a safe
drop-in for serving.

## Oracle upper bound — not deployable, but informative

The union analysis script reports an oracle union per set: the
count of theorems proved by *any* of the considered models. This
upper-bounds what any deployable router (perfect oracle) could
reach against this candidate set.

| set | gen_v5 | ns11 | ns12_balanced | ns12_replay | ns12_low_lr | **oracle** | **router** |
|---|---:|---:|---:|---:|---:|---:|---:|
| medium | 3 | 9 | 5 | 5 | 3 | **9** | **9** |
| large | — | 13 | 6 | 6 | — | **13** | **13** |
| demo_v1 | 10 | 8 | 10 | 9 | 8 | **10** | **10** |

The router *reaches the oracle* on every tested set. There is no
headroom for theorem-level routing within these models — every
theorem solved by a single-domain specialist is also covered by
that specialist's domain route. To exceed the oracle would require
either (a) a model that proves a theorem no other does, or (b) an
ensemble-vote scheme. Neither is required given the current
results.

## What this answers

1. **Does routing beat the best single checkpoint?** Yes — on
   demo_v1 it beats ns11_combined (+2), on Nat it beats
   ns12_balanced (+4 medium, +7 large). Against gen_v5 it beats it
   on medium (+6) and matches on demo.
2. **Does routing reach the Pareto frontier of NS11/NS12?**
   Exactly. It's the single dominant point: 9 medium, 13 large, 10
   demo.
3. **Can a perfect oracle do better than the router?** Not on
   these sets. Oracle union = router score on all three.
4. **Does the NS9 wrapper still work with a routed base?** Yes:
   37/38 + 49/65 preserved.

## Limitations

- The router is hand-coded per domain. It assumes the *domain
  prefix* fully predicts which model is best. This is true today
  because our models *were trained* on domain-segregated corpora
  (NS11: Nat-heavy evolve; NS12: Set/Finset-rebalanced). A model
  trained on a more heterogeneous corpus could violate this.
- Routes are matched in order; if `^Set\\.` were added before
  `^Nat\\.` it would not collide, but the schema offers no
  conflict warning. Document this in any future config.
- Theorem-level routing (per-theorem-name → model) is not
  implemented because the oracle bound shows it would not add
  anything on these eval sets. Re-evaluate if (a) we add more
  domain-specialized checkpoints, or (b) we have an eval set
  where domains overlap (e.g. a theorem that mixes Nat and
  Finset arithmetic).
- We did not test routed eval on `set_small`, `finset_small`, or
  curriculum sets — they are easy and dominated by base-model
  Aesop coverage; expected to be neutral.

## Recommendation

**Serve `routed_generative` with `ns13_router.json` as the default
raw-model surface.** It matches the oracle on every evaluation
set, doubles raw-medium coverage over gen_v5 with zero demo
regression, and preserves NS9 wrapper performance untouched. The
underlying NS11 + NS12 checkpoints remain independent and
swappable; updating either does not require retraining the other.

For NS14, the highest-leverage move is **growing the evolved
training corpus on a wider theorem-set surface** (the bottleneck
identified in NS11/NS12: 152 unique pairs is too few). Routing
gives us a clean way to incorporate a third domain-specialist
checkpoint without disturbing the existing two — just add a route
entry.
